# 内容质量自动修复闭环

本流程用于修复 `quality-rubric.md` 中失败的检查项。文案修复由 AI 执行，不是用程序自动改写文案。程序除了检查结构，还负责 A3 中可以精确比较的 GitHub 客观数据；事实矛盾与不确定性（A4）、技术层次和方向质量仍必须结合研究证据处理。

## 输入和输出边界

输入：同一个仓库的研究笔记、项目 JSON、内容质量检查结果。

输出：修复后的研究笔记和项目 JSON，以及保留失败编号的检查记录。

修复过程只能更新待发布草稿。通过检查不等于自动发布，也不能自动写入 `src/data/` 的产品数据。

## 闭环步骤

### 1. 先处理结构错误

运行 `validate_research.py` 和 `validate_project.py`。只修复明确的缺字段、数量、格式和 ID 问题，不借机重写已经合格的内容。

### 2. 生成失败清单

逐项执行 A1–E3，记录所有失败编号和能证明失败的具体句子、字段或证据缺口。不得只写“表达不好”或“方向不够新颖”。

A3 不交给 AI 猜测：程序将项目 JSON 与同一轮 GitHub 快照逐项比较。A4 不能因此放松，它继续由 AI 根据研究笔记、项目 JSON 和来源之间是否矛盾来判断。

### 3. 按风险排序

按以下顺序修复：

1. A 类事实问题。
2. B 类原项目理解和技术层次问题。
3. C 类字段串位问题。
4. D 类单个方向问题。
5. E 类整组方向问题。

后面的内容依赖前面的事实和产品理解，不能先润色方向再补证据。

### 4. 重写失败项影响的完整语义单元

- A 类失败可以修改研究笔记和受影响的事实字段。
- B 类失败通常只修改 `editorial.hook`、`editorial.summary`、`editorial.features` 或必要的术语记录。
- C 类失败通过删除、移动或收窄重复内容解决，不重写无关方向。
- D 类失败要把对应方向及其 `directionRationales`、相关 `directionComparisons` 当作一个整体；若复用能力不存在，删除该方向并基于真实能力重新生成一个。
- E 类失败先比较方向，再替换较弱或重复的方向，并同步重建所有受影响的方向依据与两两比较，不同时推翻无关方向。

每轮修复前记录准备修改的字段。这里保护的是已经通过的事实和质量要求，不是逐字冻结旧文案：为了让失败项真正成立，可以同步修改直接依赖它的字段，但没有失败编号或依赖关系支持的内容不得改动。

## 两轮修复的力度必须不同

- **第一轮——完整单元重写：** 根据失败证据定位最小语义单元，重新组织整句、整个字段或整个失败方向，不做只换一个词、补一句解释、改标题等表面修补。所有依赖该单元的证据绑定、方向依据和比较必须同步更新。
- **第二轮——替代方案重建：** 如果同一编号仍失败，丢弃第一轮失败方案，从已验证事实重新选择表达角度或产品方向。D3 失败时替换整个失败方向；E1 失败时替换较弱方向并重新生成相关比较。第二轮不得沿用评审已经指出无效的核心工作流、差异理由或句式骨架。

每轮开始前都要向修复者提供：当前失败项的原句与具体证据、失败的单方向审核、失败的方向组合审核，以及当前已通过项。已通过项用于保护质量约束；失败审核用于决定需要重建多大的单元。

## 各类失败的固定修复动作

### A1–A4：事实问题

1. 回到缺口对应的一手来源，只做有目标的补充研究。
2. 新事实写入研究笔记并分配事实 ID，再修改页面字段。
3. 找不到证据时使用 `未知`、降低推断信心或删除主张。
4. 不得通过换一种肯定语气掩盖缺少证据。

如果一手来源冲突，或关键状态可能改变是否收录，立即暂停并询问用户。

### B1–B4：项目理解或技术层次问题

1. 先用一行内部句子写清“输入或连接 → 核心操作 → 可见结果”。
2. 用它修复摘要，只补形成产品画面所缺的一环。
3. 保留前端、后端、API 等有助于理解和复用的基础概念。
4. 对更专业的术语逐个询问：删除它会不会让读者误判产品能力或复用方式？不会就删除；会就保留并解释作用。
5. 不用“某种神奇技术”“系统自动处理”等失真大白话代替关键机制。
6. 如果 B1 因 Hook 中文不自然而失败，先把想表达的事实还原成普通完整句，再从中保留一个最有辨识度的输入、动作或结果。逐一检查动宾搭配、修饰指向和相邻名词关系；宁可少表达一个能力，也不靠生造抽象词压缩篇幅。
7. Hook 的自然度修复必须整句重写，不能只替换被指出的某个词。把新句脱离项目名朗读一遍；如果还需要解释某个词组“其实想说什么”，继续从事实重新组织句子。

### C1–C4：字段串位或重复

把问题句子分别归入以下唯一职责：

- `editorial.hook`：为什么值得记住。
- `editorial.summary`：原项目怎样工作。
- `editorial.meaning`：能力为什么值得复用。
- `editorial.opportunity`：能力或限制怎样连接到新机会。

一句话有两个职责时拆开；两个字段承担同一职责时保留信息更具体的一处，删除另一处。随后检查原项目用户、新方向用户、完整流程和最小功能有没有串位。

### D1–D4：单个方向不成立

按顺序补全：具体用户与重复场景 → 输入 → 核心流程 → 可见结果 → 复用能力与事实 ID → 实质差异 → 3–6 项最小功能。

先把原项目和新方向都压缩成“用户 + 输入 → 核心工作流 → 可见结果”，逐轴比较。少于两项实质变化时，放弃该方向并重新生成，不继续润色标题。只选择原项目的一类文件、隐藏配置、改行业或把已有 API/pipeline 单独命名，都按失败处理。基础设施方向只有在原项目尚未提供相同接口，并形成新的调用者、输入约定、处理流程和返回结果时才保留；整组最多一个。

如果补全时只能依靠并不存在的能力，或差异仍然只是加 AI、移动化、翻译、换行业等弱变化，同样放弃该方向并重新生成。

### E1–E3：整组方向质量不足

1. 为每个方向列出“用户、输入、核心工作流、可见结果”。
2. 枚举所有两两组合，由复检者根据实际方向文案重新判断差异，不直接采用生成者声明的差异轴。
3. 少于两项实质不同时，保留问题更具体、证据更强、与原项目变化更大的方向，替换另一个；只更换文件类型、职业、行业、界面或输出格式的同一管线仍视为换皮。
4. 把“提高效率、促进增长”等泛化价值改成用户实际少做了什么、得到什么或保留了什么。
5. 如果全部方向都是营销、销售或赚钱流程，且用户没有要求纯商业主题，替换其中至少一个，使其主要服务于个人、家庭、学习、创作或社区。

## 复检和停止条件

每轮修改后：

1. 重新运行两个结构校验器。
2. 重新检查原失败编号。
3. 检查本轮修改是否引入新的失败编号。
4. 在记录中写明“已通过、仍失败或新增失败”。

复检只以当前版本决定能否继续，已被修复的上一轮结构错误不得继续阻塞。初检和每轮复检仍要永久保留在本轮审计记录中，包括失败证据、结构错误、阻断项、采用的策略和实际改动字段。

结果按以下规则处理：

- **全部通过：** 保存为发布候选草稿，停止自动修复；不自动发布。
- **仍然失败：** 对同一编号使用替代方案重建。可以扩大到失败语义单元的直接依赖字段，但不能扩大到无关页面内容。
- **两种方案都失败：** 停止，向用户展示原句、两个方案、失败原因和需要决定的问题。
- **出现新失败：** 撤回导致新失败的那部分改写，再尝试不会破坏已通过项的方案。
- **证据不足：** 返回 A 类研究修复；不能用更多文案代替证据。
- **需要改变产品标准：** 立即询问用户，不得为了通过检查自行改标准。

自动修复的目标是消除明确失败，不是让文案无限变化。已经通过的事实和质量要求保持稳定；只有修复失败语义单元所必需的依赖字段可以随之调整。
