# Extension direction guide

Use this guide after repository facts and page-field evidence are complete. Directions are product inferences, not documented repository features.

## Start from reusable capability

Before naming directions, list the repository's reusable capability units. Examples include a rendering engine, collaborative canvas, local search index, workflow executor, timeline model, media metadata, plugin system, or export pipeline.

Do not start from industries or fashionable technologies. A valid direction begins with a verified capability and changes the user, recurring problem, workflow, or outcome.

## Build one complete direction

Each direction must answer:

1. Who repeatedly encounters the problem?
2. What concrete situation triggers it?
3. What does the user provide or connect?
4. What does the product do with the reused capability?
5. What visible outcome does the user receive?
6. How is this workflow substantively different from the original project?
7. Which 3–6 functions are necessary for the smallest coherent experience?

If one of these cannot be answered concretely, narrow or reject the direction.

## Diversity across the set

The 3–5 directions should not be the same workflow with different professions inserted. Vary at least two of these dimensions across the set:

- Input
- User group
- Frequency of use
- Collaboration model
- Privacy model
- Output format
- Core workflow
- Human value created

Keep commercial directions when they naturally fit the repository. Unless the user explicitly requests a purely commercial theme, at least one of the 3–5 directions must primarily serve personal, family, learning, accessibility, privacy, community, or creative value rather than marketing, sales, or revenue work.

## Reject weak transformations

Reject a direction when its only difference is:

- Add AI
- Make it mobile
- Translate it
- Target an industry
- Add a dashboard
- Charge money
- Simplify the interface

Any of these may be part of a valid direction, but it must also introduce a concrete workflow and outcome.

## Evidence and honesty

- Cite the verified fact IDs for the capabilities being reused.
- Clearly separate new product logic from existing repository functionality.
- Do not claim demand without appropriate Issues, Discussions, or other primary evidence.
- Do not claim implementation ease solely because the repository is open source.
- Consider license, architecture, deployment burden, and missing capabilities when describing the approach.

## Final comparison

Before delivery, compare every pair of directions across audience, input, core workflow, and visible outcome. Every pair must differ on at least two of those four dimensions; otherwise rewrite or remove the weaker one. A newcomer should be able to explain why each direction is a different product.
