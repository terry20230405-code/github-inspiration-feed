# 后续阶段：安全自动化总控工作流

本阶段建立在阶段八的版本控制与回滚之上，把阶段六的 GitHub 数字刷新、阶段七的来源复查和工程校验串成一条可恢复的流水线。它的目标不是“无人看管地改文案并发布”，而是让重复步骤自动运行，并在需要 AI 判断或用户决定时停在准确的位置。

## 三个执行者

| 执行者 | 自动完成的工作 | 不能自行完成的工作 |
| --- | --- | --- |
| 确定性脚本 | 检查代码、比较 GitHub 数据、写入安全快照、生成来源证据、输出统一报告 | 理解 README 的语义、改中文内容、决定是否继续收录、发布 |
| AI | 阅读待审核证据，写指纹匹配的语义审核；必要时生成并修复候选草稿 | 绕过关键状态、把草稿写进产品数据、替用户做产品取舍 |
| 用户 | 处理仓库转移、许可证变化、归档或重大转向；批准最终发布 | 日常重复执行命令、手动比较 Star 或 README 哈希 |

## 三个命令

### 1. 只检查

```powershell
npm run refresh:cycle
```

先运行全部测试、Lint 和生产构建，再执行阶段六、阶段七的 dry-run。它不会写入仓库快照和来源状态，适合手动预览这次刷新会发生什么。

### 2. 安全写入

```powershell
npm run refresh:cycle:write
```

运行顺序：

1. 工程预检：阶段六、阶段七、视觉身份和总控脚本测试，加上 Lint 与生产构建。
2. 阶段六 dry-run：发现关键变化就停止，不写任何刷新数据。
3. 阶段六 write：只写 `repository` 快照、缓存和报告。
4. 阶段七 dry-run：发现关键来源问题就停止，不写来源状态。
5. 阶段七 write：只写来源状态、缓存、报告和待审核证据包。
6. 写入后再次运行 Lint 和生产构建；失败时由阶段八快照自动回滚。
7. 根据统一状态决定下一位执行者。

### 3. AI 审核后继续

```powershell
npm run refresh:cycle:resume
```

AI写完并验证 `*.review.json` 后使用。它不会重复阶段六，而是让阶段七重新识别当前来源指纹对应的审核结论，然后重新执行 Lint 和生产构建。

## 统一状态

总控报告保存在 `outputs/automation/latest.json`，每次运行的历史副本保存在 `outputs/automation/runs/`。

| `status` | 含义 | 下一位执行者 |
| --- | --- | --- |
| `check-completed` | 预演安全，可以决定是否正式写入 | AI 或用户启动 write |
| `completed` | 本轮没有内容工作 | 无 |
| `ai-review-required` | 有新的来源证据，需要语义判断 | AI |
| `content-draft-required` | 审核证明页面内容可能过时，需要生成候选草稿 | AI |
| `human-decision-required` | 许可证、仓库身份、归档或重大转向等关键问题 | 用户 |
| `failed` | 命令、网络、限流、数据格式或工程检查失败 | AI先排查；涉及外部权限再询问用户 |

所有状态都固定带有 `publicationAuthorized: false`。`completed` 只代表刷新流程完成，不代表网页已经部署。

## 自动化代理的续跑规则

定时运行本流程的 AI 应按以下规则工作：

1. 执行 `npm run refresh:cycle:write`，读取 `outputs/automation/latest.json`。
2. `completed`：只报告本轮更新数量，不制造额外内容。
3. `ai-review-required`：读取最新 `*.source.json` 与当前已发布内容，按阶段七协议生成 `*.review.json`，逐个运行 `validate:research-review`，然后执行 `refresh:cycle:resume`。
4. `content-draft-required`：按研究协议生成 `.research.md` 和 `.project.json`，完成结构校验、19 项质量检查和最多两种针对性修复；产物只留在 `outputs/generated/`。
5. `human-decision-required`：停止并把事实、风险和需要选择的问题交给用户，不继续刷新或改文案。
6. `failed`：先尝试一次有明确依据的技术修复；如果是 GitHub 限流、Token、网络或外部服务问题，停止并说明需要什么。

AI不能因为一次定时任务而获得发布权限。把候选草稿加入 `src/data/`、推送代码或部署网站，仍然需要用户明确要求，或者后续单独建立具有清晰授权范围的发布阶段。

## 防重复与恢复

- `outputs/automation/refresh.lock` 防止两个定时任务同时改同一批文件；正常结束后自动删除。
- 意外中断可能留下锁文件。先确认没有刷新进程仍在运行，再人工删除这一张锁文件；不要删除整个 `outputs/automation/`。
- 总控脚本的成功退出码为 `0`，其中可能包含“下一步交给 AI”的正常暂停状态。
- 关键人工决策返回 `2`；技术失败返回 `1`。
- 来源指纹、ETag 和已保存状态保证重复运行不会把同一变化当成无限的新任务。

## 当前不在阶段八内的事项

- 没有创建固定运行时间；频率和时间需要用户决定。
- 没有接入托管平台，因此刷新本地数据后不会自动更新公网网页。
- 没有自动发布候选文案，也没有自动添加新仓库。
- 没有把 GitHub Token 写入项目；Token 只能由运行环境通过 `GITHUB_TOKEN` 提供。

这些不是遗漏，而是不同权限层级。定时、部署和发布应在运行环境与授权边界明确后再分别接入。
