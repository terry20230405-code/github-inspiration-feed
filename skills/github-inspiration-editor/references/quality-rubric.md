# 内容质量检查标准

这套标准判断仓库研究笔记和项目 JSON 能否进入发布候选。校验器检查格式，本文检查内容。评审必须同时查看 `<owner>-<repo>.research.md` 和 `<owner>-<repo>.project.json`；没有研究笔记的内容不能通过事实检查。

## 目标读者

目标读者了解 Vibe Coding 的基本概念，可以直接理解“前端、后端、API”等常用词，但不会阅读代码，也不应被要求理解底层实现原理。

不要为了口语化而删除有助于理解产品或判断复用方式的基础技术词。只有在术语属于底层细节、不能帮助理解产品工作方式或复用价值时，才省略它；必要的专业词应紧接一句简短的作用说明。

## 判断方式

每个检查项只有两种结果：`通过` 或 `失败`。检查结果可以写成“通过项数 / 总项数”，但这个数字只表示修复进度，不是平均分，也没有及格线。

发布候选必须满足：

- 两个结构校验器通过。
- 下列 19 个必要检查项全部通过。
- 没有“必须暂停”的情况。

不允许用其他项目的高分抵消一个项目的问题，也不允许用表达流畅抵消事实错误。

自动发现流程会先生成五个候选方向，评审完整检查五个方向和十组两两关系后，选出三个最终方向。下面 D、E 类的发布结论只针对这三个入选方向；未入选方向可以失败，但不能进入项目 JSON。三个入选方向仍须完整通过所有相关检查，这一筛选不降低最终发布标准。

## A. 事实完整性

- **A1 事实可追溯：** `repository` 中的 GitHub 事实，以及 `editorial.summary`、`editorial.audience`、`editorial.features` 和 `editorial.stack` 中的事实都指向研究笔记里的事实 ID；事实 ID 引用了已登记的一手来源。
- **A2 推断有边界：** `editorial.hook`、`editorial.meaning`、`editorial.opportunity` 和每个方向都能指出所依据的事实；研究笔记把推断与原项目功能明确分开。
- **A3 关键状态准确：** `repository.githubId`、`repository.fullName`、许可证、仓库状态和 `fetchedAt` 准确；Star、Fork 和推送时间保存原始值，没有被描述成实时值。
- **A4 不确定就保留不确定：** 研究笔记、项目 JSON 与来源之间没有矛盾；无法验证的内容写成 `未知`、降低信心或从页面主张中删除，没有用猜测补齐。

## B. 原项目是否讲清楚

- **B1 Hook 有项目特征且中文自然：** `hook` 使用该项目真实的输入、动作、结果或独特能力建立记忆点，不依赖“强大、创新、一站式”等评价词。它单独出现时也必须像自然中文：动词和宾语搭配合理，修饰关系清楚，相邻名词的关系不用读者猜测；不能照着英文结构直译、堆叠抽象名词，或为了压缩多个能力而生造短语。事实意思正确但表达不像人会说的话，仍判定失败。
- **B2 工作方式完整：** `summary` 说明项目接收或连接什么、用户进行什么核心操作、最后得到什么可见结果。
- **B3 核心能力足够：** `summary` 与 `features` 共同覆盖至少三个有证据的核心能力；摘要只保留形成产品画面所必需的能力，不堆砌次要功能。
- **B4 技术层次合适：** 前端、后端、API 等有助于理解或复用的基础词可以直接保留；更专业的词只有在影响产品理解或复用判断时才出现，并说明它在产品中起什么作用。不能把重要技术能力全部改写成失真的大白话。

## C. 页面字段是否各司其职

- **C1 Hook 与摘要分工：** `hook` 只建立记忆点，不列功能；`summary` 建立原项目的完整产品画面，不重复 hook 的句子。
- **C2 事实与改造价值分工：** `summary` 只介绍原项目；`meaning` 只解释已有能力为什么值得复用，不把新方向写成现有功能。
- **C3 意义与拓展依据分工：** `meaning` 给出总体复用价值；`opportunity` 逐条连接“已验证能力或限制 → 具体摩擦 → 新产品可能性”，不能只写“可以加 AI”。
- **C4 用户和范围不串位：** 项目 `audience` 只描述原项目用户；方向 `audience` 只描述新产品用户；`approach` 讲完整流程，`scope` 只列支撑该流程的最小功能。

## D. 每个改造方向是否成立

以下四项必须对最终入选的每一个方向分别检查；任意一个入选方向失败，整个检查项失败。

- **D1 用户问题具体：** 写明一类具体用户，以及会重复发生的场景或问题，不使用“所有人”或宽泛行业趋势。
- **D2 流程可以演示：** 写明用户输入或连接什么、产品经过哪些核心步骤、用户看到什么结果。
- **D3 复用和差异真实：** 指出复用的已验证能力及事实 ID；逐个写出原项目与新方向的“用户、输入、核心工作流、可见结果”，至少有两项发生实质变化。只挑选原项目的一类文件或一组工具、隐藏配置、改行业名称、增加界面，或把原项目已有的 API、pipeline、插件接口单独包装，都不能算新产品。基础设施方向最多一个，而且必须形成原项目尚未提供的重复集成流程和结果。
- **D4 第一版范围闭合：** `scope` 的 3–6 项功能足以完成前述流程，没有混入可选装饰、以后再做的路线图或开发排期。

## E. 一组方向是否值得同时展示

- **E1 方向不是换皮：** 必须列出所有方向两两组合，并由评审根据实际文案独立核对“用户、输入、核心工作流、可见结果”；任意一对至少有两项实质不同。围绕同一处理管线只更换文件类型、职业、行业、界面或输出格式，合计只能算一项变化；否则删除或重做较弱方向。不能直接相信生成阶段自行声明的差异轴。
- **E2 每个方向有具体价值：** 每个方向都说明给具体的人减少了什么麻烦、创造了什么体验或保留了什么重要事物，不能只承诺“提高效率、促进增长、更加智能”。
- **E3 默认保留非商业价值：** 商业方向可以正常出现；除非用户明确要求纯商业主题，3–5 个方向中至少有一个主要服务于个人、家庭、学习、创作或社区，而不是营销、销售或赚钱流程。

## 必须暂停并询问用户

遇到以下情况不能自行选择模棱两可的标准：

- 两个一手来源对许可证、仓库身份、归档状态或核心能力给出冲突信息。
- 修复需要改变目标读者、商业方向原则、页面字段职责或其他产品内容契约。
- 许可证、仓库转移、归档或产品重大转向可能影响是否继续收录。
- 同一个检查项先后经过一次针对性修复和一次不同方案的替代修复，仍然失败。
- 多种方向都成立，但选择会明显改变产品主题，且用户没有给出主题偏好。

普通措辞选择、证据充分时的内容取舍和不改变产品定位的方向优化不需要询问用户。

## 评审记录

每个失败项必须记录：检查编号、失败证据、准备修改的字段和修复结果。不要为已经通过的字段制造改写。

```markdown
# 内容质量检查

- 项目：owner/repo
- 日期：YYYY-MM-DD
- 固定研究证据：path
- 结果：通过项 / 19
- 发布候选：是 / 否

## 失败项

- B4
  - 失败证据：摘要使用底层术语，但没有帮助理解产品或复用方式。
  - 修改字段：summary
  - 修复动作：保留有用的基础概念，删除或解释无关底层词。
  - 复检结果：通过 / 失败

## 必须询问用户的问题

- 无。
```

低分后的修复顺序和停止条件见 [quality-repair-loop.md](quality-repair-loop.md)。修改 Skill 本身时，再使用 [benchmark-set.md](benchmark-set.md) 做固定案例比较。
