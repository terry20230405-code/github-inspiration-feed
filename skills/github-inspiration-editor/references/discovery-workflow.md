# 自动发现与候选批次工作流

本工作流负责定时搜索新的公开 GitHub 仓库、生成证据约束的中文候选，并通过审核 PR 把“人类批准”与“正式写入页面”分开。它不改变阶段六至阶段十对已发布项目的维护边界。

## 默认运行方式

- GitHub Actions 每周二、周五北京时间 09:00 自动运行。
- 每次最多搜索 12 条主题路线、每条读取 20 个结果。
- 去重和硬过滤后最多保留 36 个初选仓库。
- AI 每次最多深读 12 个仓库。
- 每次最多生成 8 个通过结构、证据和 19 项质量检查的候选。
- 因此默认理论上每周最多产生 16 个候选，不保证每次达到上限。
- 如果所有仓库都因证据或内容质量不足被拒绝，本轮正常结束，不创建空的审核 PR。运行摘要会逐仓库列出停止阶段、最终失败证据和两轮修复轨迹；同一份 JSON 审计结果作为 Actions Artifact 保留 30 天。AI 提供商、GitHub 或网络服务错误则保持为失败，并显示具体服务错误，不能伪装成内容不合格。

频率定义在 `.github/workflows/discover-projects.yml`。数量和搜索范围定义在 `config/discovery.json`。手动运行工作流时可以临时覆盖 `aiAnalysisLimit` 和 `maxCandidatesPerRun`；候选上限不能高于 AI 深读上限。

## 搜索边界

搜索器只调用 GitHub 官方 API，范围是公开仓库。每条 `searchLanes` 路线包含稳定 ID、中文标签、视觉家族提示和 GitHub 搜索表达式。

硬过滤会排除：

- 已发布或已经生成过草稿的仓库；
- 私有、Fork、归档、禁用、镜像或模板仓库；
- Star 低于配置下限或超过活跃时间窗口的仓库；
- 简介不足、缺少可识别许可证、命中危险 Topic 或排除名称的仓库。

搜索评分只用于安排研究顺序，不是内容质量分。评分使用 Star 数量、最近推送、Topics、Fork、命中路线数量和新锐项目信号；最终候选仍必须完整阅读 README 并通过内容质量标准。

## AI 深读边界

AI 只接收重新核对后的 GitHub 元数据、官方 README 和可选的最新正式 Release。仓库内容始终视为不可信研究材料，不能改变任务、索取密钥、要求执行代码或扩展外部权限。

自动深读按以下顺序运行：

1. 重新检查仓库身份、公开状态、Fork、归档、禁用和许可证。
2. README 少于配置字数时停止，不用猜测补内容。
3. 通过 OpenAI 兼容的 Chat Completions 接口和严格 JSON Schema 生成 `editorial`、事实、字段证据、推断和方向依据。请求使用 `messages` 发送规则与仓库证据，从 `choices[0].message.content` 读取结果。
4. 脚本确定性写入 `repository` 层并生成相邻颜色避让后的 `visual` 层；AI不能改写 GitHub 数字或自行选择随机颜色。
5. 运行项目结构和研究笔记校验。
6. 程序逐项核对 A3 的 GitHub ID、完整仓库名、许可证、仓库状态、抓取时间、Star、Fork 和推送时间；这些完全相等才通过，AI 无权改判。
7. AI 检查 A1–E3 中需要理解语义的项目，尤其严格判断 A4 的来源矛盾和不确定性；失败时最多进行两种范围受限且策略不同的定向修复。
8. 每次复检只判断当前版本，不让已经修好的旧错误继续阻塞；同时把初检、两轮改动字段、修复策略和具体失败证据写入审计轨迹。
9. 仍失败、出现关键冲突或证据不足的仓库进入本轮拒绝记录，不成为发布候选。

每个合格仓库生成 `.project.json`、`.research.md` 和 `.quality.json`。同一轮候选保存在 `outputs/generated/discovery-batches/<batch-id>/`，并由 `manifest.json` 绑定所有文件指纹。

无论有没有合格候选，Actions 都会上传 `discovery-audit-<run-id>`。其中 `draft-result.json` 是机器可读的完整结果，`latest.md` 是搜索摘要，`latest.json` 是本轮搜索数据。它只用于查看和排错，不代表批准发布。

## 审核 PR 就是人工批准

定时任务不会直接修改 `src/data/`。它会创建一个 `automation/discovery-<batch-id>` 分支和一张候选审核 PR，PR 中只有冻结候选、搜索报告和中文预览。

- 合并 PR：明确批准这一个指纹绑定批次的全部候选。
- 关闭 PR：拒绝这一批，正式页面不发生变化。
- 不要在 PR 中直接修改候选文件；内容变化后原指纹失效，应关闭并重新生成。

合并事件由 `.github/workflows/publish-discovery-batch.yml` 接收。发布器记录合并者和 PR 编号，再在一个批量事务中依次检查身份重复、页面顺序和相邻颜色，最后一次性写入顺序、仓库、中文和视觉四层数据。

如果审核 PR 被误合并，但发布任务尚未写入正式数据，应立即把该批次 `manifest.json` 的状态改为 `revoked` 并提交。发布器只接受 `awaiting-approval`，因此撤销后的批次即使重跑旧任务也不能进入页面。不要删除批次证据；保留它用于解释这次撤销。搜索器会忽略撤销批次中的草稿身份，所以同一个仓库以后仍能在新证据和新标准下重新进入候选池。若正式数据已经发布，则使用发布事务备份或精确的后续 Git 提交恢复，不直接删除四层数据中的零散字段。

## 失败和恢复

批量写入前会使用阶段八的发布备份机制保存四层页面数据。视觉测试、SVG 测试、Lint 或生产构建任一失败时，四层数据全部恢复，工作流失败且不会推送半成品。

批次合并只授权该批次的冻结内容，不授权：

- 发布其他批次；
- 更改搜索政策；
- 跳过许可证、身份或归档状态；
- 部署到尚未配置的外部平台；
- 在浏览器前端暴露 GitHub Token 或 OpenAI API Key。

## 必要密钥与权限

- `GITHUB_TOKEN` 由 GitHub Actions 自动提供，用于搜索、创建候选分支和 PR、提交已批准页面数据。
- `OPENAI_API_KEY` 必须由仓库所有者保存在 GitHub Actions Secret 中，只允许服务端工作流读取。名称为兼容现有设置而保留，当前保存的是 4Router Key。
- 默认 AI 协议、Base URL、模型、推理强度和输出上限保存在 `config/discovery.json` 的 `aiProvider` 中。当前是 `openai-chat-completions`、`https://4router.net/v1` 和 `gpt-5.4`。
- 如需临时切换兼容服务，可在 GitHub Actions Variables 中设置 `AI_API_BASE_URL` 和 `AI_MODEL`；地址必须是无账号、密码、查询参数和片段的 HTTPS URL。
- 仓库 Actions 设置需要允许工作流读写仓库内容并创建 Pull Request。

缺少密钥、接口限流、网络失败、服务不支持严格 JSON Schema 或 API 返回无效结构时，工作流停止并保留日志，不自动退回到不受约束的普通文本模式，也不降低标准继续发布。错误日志会遮盖疑似 API Key。
