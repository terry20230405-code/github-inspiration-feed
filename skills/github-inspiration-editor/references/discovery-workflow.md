# 自动发现与候选批次工作流

本工作流负责定时搜索新的公开 GitHub 仓库、生成证据约束的中文候选，并通过审核 PR 把“人类批准”与“正式写入页面”分开。它不改变阶段六至阶段十对已发布项目的维护边界。

## 默认运行方式

- GitHub Actions 每周二、周五北京时间 09:00 自动运行。
- 每次新项目搜索前先运行一次已发布项目安全巡检；刷新成功时自动提交仓库数字、来源状态、审计报告和事务快照。仓库身份、许可证或状态等关键变化会留下警告和人工待办，但不会让已经成功的新项目发现与候选 PR 变成失败；真正的网络、API 或数据错误仍会把工作流标记为失败。
- 每次最多搜索 12 条主题路线、每条读取 20 个结果。
- 去重和硬过滤后最多保留 36 个初选仓库。
- AI 每次最多深读 12 个仓库。
- 每次最多生成 8 个通过结构、证据和 19 项质量检查的候选。
- 不同仓库最多并发深读 3 个，并采用持续补位：任意一个仓库完成后立刻补入下一个，不等待同组最慢仓库；单个仓库内部仍按生成、审核、修复和复审的依赖顺序串行执行。最终结果按原始候选顺序汇总，项目 ID 与视觉身份也按该顺序生成，不能因并发改变排序或相邻颜色避让。
- 因此默认理论上每周最多产生 16 个候选，不保证每次达到上限。
- 如果所有仓库都因证据或内容质量不足被拒绝，本轮正常结束，不创建空的审核 PR。运行摘要会逐仓库列出停止阶段、最终失败证据和两轮修复轨迹；同一份 JSON 审计结果作为 Actions Artifact 保留 30 天。AI 提供商、GitHub 或网络服务错误则保持为失败，并显示具体服务错误，不能伪装成内容不合格。

网络故障和内容质量失败必须分开：断线、连接重置、响应截断等临时读取故障最多尝试三次，重试使用同一份严格结构请求，不消耗内容修复轮次；密钥、权限、地址或接口参数等确定性错误不盲目重试，并停止向剩余候选发起新任务。已在执行的候选会完成各自检查。重试可能重复计费，因此不能无限重试。

一个候选遇到服务故障不能清空其他候选。合格项仍生成正常的指纹批次并可创建审核 PR；技术故障单独记录在 `errors` / `errorCount`，不计入质量拒绝数量。CLI 输出完整结果后以非零状态退出，Actions 先保存报告和合格批次、运行验证、创建合格候选的审核 PR，再报告整轮技术失败。该 PR 合并仍只批准其中已验证的候选；失败项不进入批次。没有合格项时不创建 PR。进程被强制终止或主机丢失不属于这一候选级隔离机制的恢复保证。

旧项目巡检与新项目发现共享同一个定时触发，但权限边界不同。巡检只能自动修改 `src/data/repositories.json` 及阶段六至阶段八规定的刷新状态、证据、报告和快照；绝不能修改 `src/data/editorial.json`、`src/data/visuals.json` 或 `src/data/order.json`。来源语义发生变化时只留下待复审证据，不能把“本次定时运行”解释为自动重写或发布旧项目内容。

两部分拥有独立结果：旧项目巡检的 `review-required` 在 Actions 中显示为 warning，并继续保留 `published-refresh-audit`；新项目发现按自己的搜索、深读、测试与 PR 创建结果决定成功或失败。警告不等于批准旧项目关键变化，也不会撤销、删除或阻断本轮已经冻结的新候选。

频率定义在 `.github/workflows/discover-projects.yml`。数量和搜索范围定义在 `config/discovery.json`。手动运行工作流时可以临时覆盖 `aiAnalysisLimit` 和 `maxCandidatesPerRun`；候选上限不能高于 AI 深读上限。

## 搜索边界

搜索器只调用 GitHub 官方 API，范围是公开仓库。每条 `searchLanes` 路线包含稳定 ID、中文标签、视觉家族提示和 GitHub 搜索表达式。

硬过滤会排除：

- 已发布或已经生成过草稿的仓库；
- 私有、Fork、归档、禁用、镜像或模板仓库；
- Star 低于配置下限或超过活跃时间窗口的仓库；
- 简介不足、缺少可识别许可证、命中危险 Topic 或排除名称的仓库。

搜索评分只用于安排研究顺序，不是内容质量分。评分使用 Star 数量、最近推送、Topics、Fork、命中路线数量和新锐项目信号；最终候选仍必须完整阅读 README 并通过内容质量标准。

## AI 深读边界

AI 只接收重新核对后的 GitHub 元数据、官方 README、官方 LICENSE 文件和可选的最新正式 Release。仓库内容始终视为不可信研究材料，不能改变任务、索取密钥、要求执行代码或扩展外部权限。许可证优先依据 GitHub 检测结果和官方 LICENSE 文件；README 徽章不能单独推翻正式许可证文件。

自动深读按以下顺序运行：

1. 重新检查仓库身份、公开状态、Fork、归档和禁用，并额外读取 GitHub 官方 LICENSE 端点。标准许可证以 SPDX 身份核对，非标准许可证尝试从正式许可证文件标题保存准确名称；两个正式来源确实冲突时才停止人工确认。
2. README 少于配置字数时停止，不用猜测补内容。
3. 通过 OpenAI 兼容的 Chat Completions 接口和严格 JSON Schema 生成 `editorial`、事实、字段证据、推断和方向依据。每个仓库先生成五个完整候选方向以及十组两两比较，为淘汰弱方向留下余量。请求使用 `messages` 发送规则与仓库证据，从 `choices[0].message.content` 读取结果。
4. 脚本确定性写入 `repository` 层并生成相邻颜色避让后的 `visual` 层；AI不能改写 GitHub 数字或自行选择随机颜色。
5. 运行项目结构和研究笔记校验。
6. 程序逐项核对 A3 的 GitHub ID、完整仓库名、许可证、仓库状态、抓取时间、Star、Fork 和推送时间；这些完全相等才通过，AI 无权改判。
7. 每个方向必须提交原项目/新流程对照、至少两个实质变化轴和产品边界；五个候选方向的十种两两组合也必须提交差异表。程序检查表格完整且整组最多一个基础设施方向，AI 再独立核对这些差异是否真实，不能把已有 API 或同一处理管线换名字当成新产品。
8. AI 审核全部五个方向和十组组合，并按原顺序选出三个最终方向。只有入选方向及其组合决定 D、E 类是否通过；未入选的弱方向可以失败，不再拖垮整个仓库。最终项目 JSON 和研究笔记只保存三个入选方向。
9. AI 检查 A1–E3 中需要理解语义的项目，尤其严格判断 A4 的来源矛盾和不确定性。19 项结果使用 A1–E3 固定键返回，由程序按固定顺序转换，不能因数组漏项或乱序误伤候选；若评审结论结构无效或自相矛盾，系统只重试评审，不改写内容，也不占用两轮内容修复机会。内容确实失败时，才最多进行两种范围受控但力度不同的修复：第一轮重写完整失败语义单元，第二轮丢弃失败方案并从已验证事实重建替代方案。
10. 每次复检只判断当前版本，不让已经修好的旧错误继续阻塞；同时把初检、两轮改动字段、修复策略、三个入选方向和具体失败证据写入审计轨迹。
11. 仍失败、出现关键冲突或证据不足的仓库进入本轮拒绝记录，不成为发布候选。

只要不存在必须人工决定的阻断项，首轮修复后仍失败就必须执行第二轮替代方案重建；D3 或 E1 第一轮没有改善也不能提前跳过。第二轮会增加一次修复和一次复检调用，但不能降低标准或把失败改成通过。

修复请求只传一份一手证据和上一版生成对象，不重复传送可确定性派生的项目 JSON 与研究笔记；同时传入当前失败项、失败的单方向审核、失败的方向组合审核、结构错误和已经通过的质量约束。第一轮允许同步更新失败语义单元的直接依赖字段，第二轮必须舍弃已被证明无效的方案；修复后仍须重新生成并完成结构、A3 和语义复检。

每轮 `draft-result.json` 和 Actions 摘要记录候选并发上限、每次 AI 调用阶段、耗时、输入字符数、重试次数，以及中转接口实际返回时的 Token 用量。统计不得保存提示词正文、API Key 或其他密钥。

每个合格仓库生成 `.project.json`、`.research.md` 和 `.quality.json`。同一轮候选保存在 `outputs/generated/discovery-batches/<batch-id>/`，并由 `manifest.json` 绑定所有文件指纹。

无论有没有合格候选、深读步骤是否失败，Actions 都会尝试上传 `discovery-audit-<run-id>`。其中 `draft-result.json` 是机器可读的完整结果，`latest.md` 是搜索摘要，`latest.json` 是本轮搜索数据；成功冻结的候选批次也随附件保留，以防后续测试或创建 PR 时失败。新项目摘要追加到旧项目巡检摘要后，不能覆盖旧结果。附件只用于查看和排错，不代表批准发布。

## 审核 PR 就是人工批准

定时任务不会直接修改 `src/data/`。它会创建一个 `automation/discovery-<batch-id>` 分支和一张候选审核 PR，PR 中只有冻结候选、搜索报告和中文预览。

- 合并 PR：明确批准这一个指纹绑定批次的全部候选。
- 关闭 PR：拒绝这一批，正式页面不发生变化。
- 不要在 PR 中直接修改候选文件；内容变化后原指纹失效，应关闭并重新生成。

合并事件由 `.github/workflows/publish-discovery-batch.yml` 接收。发布器记录合并者和 PR 编号，再在一个批量事务中依次检查身份重复、页面顺序和相邻颜色，最后一次性写入顺序、仓库、中文和视觉四层数据。

如果审核 PR 被误合并，但发布任务尚未写入正式数据，应立即把该批次 `manifest.json` 的状态改为 `revoked` 并提交。发布器只接受 `awaiting-approval`，因此撤销后的批次即使重跑旧任务也不能进入页面。不要删除批次证据；保留它用于解释这次撤销。搜索器会忽略撤销批次中的草稿身份，所以同一个仓库以后仍能在新证据和新标准下重新进入候选池。若正式数据已经发布，则使用发布事务备份或精确的后续 Git 提交恢复，不直接删除四层数据中的零散字段。

## 失败和恢复

批量写入前会使用阶段八的发布备份机制保存四层页面数据。视觉测试、SVG 测试、Lint 或生产构建任一失败时，四层数据全部恢复，工作流失败且不会推送半成品。

批次合并只授权该批次的冻结内容，不授权：

- 发布其他批次；
- 更改搜索政策；
- 跳过许可证、身份或归档状态；
- 部署到尚未配置的外部平台；
- 在浏览器前端暴露 GitHub Token 或 OpenAI API Key。

## 必要密钥与权限

- `GITHUB_TOKEN` 由 GitHub Actions 自动提供，用于搜索、创建候选分支和 PR、提交已批准页面数据。
- `OPENAI_API_KEY` 必须由仓库所有者保存在 GitHub Actions Secret 中，只允许服务端工作流读取。名称为兼容现有设置而保留，当前保存的是 4Router Key。
- 默认 AI 协议、Base URL、模型、推理强度和输出上限保存在 `config/discovery.json` 的 `aiProvider` 中。当前是 `openai-chat-completions`、`https://4router.net/v1` 和 `gpt-5.4`。
- 如需临时切换兼容服务，可在 GitHub Actions Variables 中设置 `AI_API_BASE_URL` 和 `AI_MODEL`；地址必须是无账号、密码、查询参数和片段的 HTTPS URL。
- 仓库 Actions 设置需要允许工作流读写仓库内容并创建 Pull Request。

缺少密钥、接口限流、网络失败、服务不支持严格 JSON Schema 或 API 返回无效结构时，工作流停止并保留日志，不自动退回到不受约束的普通文本模式，也不降低标准继续发布。错误日志会遮盖疑似 API Key。
